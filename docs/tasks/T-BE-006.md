# T-BE-006 — Role guards and accept-invite

**Status:** todo
**Module:** `src/modules/auth` and `src/common/guard/role`
**Depends on:** T-BE-005
**Priority:** P0

## Goal

Routes can require `STUDENT`, `TEACHER`, or `ADMIN`, pending students cannot call app APIs, and a teacher can accept a staff invite.

## Scope

- `Role` enum in `role.enum.ts` is `STUDENT | TEACHER | ADMIN` only.
- `RolesGuard` loads the user and compares `user.role` to `@Roles(...)`. Missing role → 403. Missing user → 401.
- New `ActiveStudentGuard`: if role is `STUDENT` and status is not `ACTIVE`, throw 422 with message `PENDING`. Staff roles pass. Use it later; export it from the auth module.
- `POST /api/auth/teacher/accept-invite`: body `token`, `password`, `name`. Hash-compare against `StaffInvite.token_hash`. Expired or already accepted → 400. Creates `User` `TEACHER` `ACTIVE` with `school_id` from the inviting admin, sets `can_access_safe_space` on the user only if you already have a column — the flag lives on `StaffInvite`. Store it in `settings_json` as `{ canAccessSafeSpace: boolean }` so T-BE-022 can read it without a schema change. Sets `accepted_at`. Returns the user. Do not add a new column in this task.
- JWT from a later staff login works. This route does not have to return a token if `docs/API.md` only says `user`. Return `{ user }`.

Invite **creation** is T-BE-010. This task’s tests insert a `StaffInvite` row.

## Out of scope

- CASL permission checks.
- Parent role.
- Creating invites, staff list, or profile screens.
- Applying the guard to future controllers (each later task adds `@UseGuards`).

## Required tests

- guard allows the matching role and rejects another role with 403.
- active-student guard rejects `PENDING` students with 422 and allows `ACTIVE` students and teachers.
- accept-invite with a bad token → 400.
- accept-invite creates a `TEACHER` and sets `accepted_at`.
- second accept of the same token → 400.
